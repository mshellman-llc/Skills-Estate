# Requirements capture

Read [shared workflow](references/estate/workflow.md). For a rendered or branded artifact, read [brand policy](references/estate/brand.md) before choosing visual values. These references are generated from the canonical policies when the estate builds.

Read the supplied brief, signed scope when relevant, existing requirements, and stakeholder evidence. Identify business outcomes, actors, system boundaries, dependencies, and unresolved decisions. Separate contract commitments from proposed backlog detail.

Build a hierarchy of epic, capability, business need, and user story with stable IDs. Trace each requirement to its source or label it a proposal. Use MoSCoW priorities consistently and distinguish proposed, reviewed, approved, in progress, and complete states. A prioritization suggestion is not stakeholder approval.

Write stories with actor, action, and value. Acceptance criteria specify observable outcomes and relevant negative cases. Use Given/When/Then when it makes conditions clearer; do not turn vague goals into invented thresholds. Include permissions, data validation, errors, and integration behavior where the requirement needs them.

For a workbook, use the available spreadsheet tool. Keep the delivery hierarchy and detailed stories/acceptance criteria in separate linked tabs unless the user supplies a different structure. Verify unique IDs, valid parent references, filters, usable column widths, and source coverage. Surface only the material questions that prevent a workable draft. Deliver an editable artifact and identify which decisions still need an owner.
