# Add, update and prepare skills

Use one reviewed Skills Estate checkout as the source. Installed folders, account caches, `build/` and `dist/` are outputs. Prepare changes in an isolated branch when the canonical checkout contains other work. Reconcile that branch before using it as the continuing authority.

1. For an addition, use Skill Estate Sync's authoring mode and its intake/scaffolder. For an update, edit the existing workflow and retain its behavior and resources. Update `config/skill-catalog.json` and `config/runtime-dependencies.json` when the entrypoint or dependencies change. A new skill must be selected explicitly in a distribution profile.
2. Run `python3 tools/estate.py validate` and the changed workflow's behavioral tests. Run `python3 tools/run_tests.py --report .local/test-results.json`. Inspect representative outputs and obtain independent review. Deferred integrations and host invocation remain separate acceptance requirements.
3. Select the audience with `python3 tools/estate.py release plan --profile personal` or `--profile telix`. The personal profile initially selects Code Simplify, Information Architecture, Writing Integrity and Skill Estate Sync. It is a limited private candidate, not the whole installed estate. Expand its explicit entries only after reviewing their complete resources. Telix selects only Code Simplify. Its complete Writing Integrity and diagnostic dependencies are retained with workplace-only portability adaptations. Preparation stays blocked until the exact generated payload has a recorded privacy review.
4. Record the change and increment the version: `python3 tools/estate.py release bump --profile personal --part patch --note 'Describe the change'`. Choose `minor` for compatible additions and `major` for incompatible changes. A version bump invalidates the previous build.
5. Run `python3 tools/estate.py sync`. Copy `source_sha256` from `build/manifest.json`, then run `python3 tools/estate.py release prepare --profile personal --expected-source HASH`. The command refuses stale build bytes, the wrong source hash, excluded entries and a changed source at an already prepared version.
6. Run `python3 tools/estate.py release verify --profile personal`. Inspect the exact generated files and ZIPs under `dist/profiles/personal/`. The Claude marketplace is `claude/.claude-plugin/marketplace.json`; each plugin has `.claude-plugin/plugin.json` beside its `skills/` directory. The Codex adapter is prepared separately. Both include complete selected runtime resources.

Preparation creates local candidates only. It does not install, upload, push, publish, create repositories or modify accounts. Its receipt records pending source review and host checks. Structural tests do not certify skill behavior or workplace privacy. Before any separately authorized distribution, complete those checks on the exact bytes, run the host's current manifest validator, and verify the intended account and audience. Do not share the private authoring repository or its history with Telix.

## Workplace review

Keep the Telix profile blocked until every generated file in the minimal package, including scripts, examples, policies, templates and transitive runtimes, has been reviewed. Do not use a keyword scan as approval. Preserve licenses and attribution. Exclude personal profile stores, client examples, employer policies and credentials. Code Simplify is the only selected entrypoint; Writing Integrity and its diagnostic runtime remain complete dependencies.

Run `python3 tools/estate.py release review --profile telix` to build a private fixture under `.local/privacy-review/telix/`. This command does not approve content, write distribution output or change the release ledger. Read every file in both host trees. After independent review of those exact bytes, record the evidence and matching `payload_sha256` in the profile's `privacy_review`, then clear `blocked_reason`. Every workplace build compares the payload with that reviewed digest, including manifests and release metadata. Only the receipt's source digest and host-adapter identifier are normalized, with their allowed forms validated separately. Any resource change, version bump, added dependency or extra file invalidates approval. Do not remove required dependencies to evade this check. The personal profile has no workplace clearance.

Workplace portability edits live in `config/workplace-reference-adaptations.json`. Each binds to the original file hash and exact passages. They replace personal setup and unverified examples only in the generated workplace package; the source and personal output retain their existing behavior. A changed source or unmatched passage blocks assembly. The workplace learning helper requires an explicit separate `--store` path and never falls back to the personal environment or default store. No store is enrolled or copied during packaging. Use core review without learned preferences until the owner confirms workplace storage.

## Receipts and recovery

Version notes and prepared candidate hashes live in `config/release-history.json`. This audit file is deliberately excluded from source hashes so writing a receipt does not invalidate its own build. It is never copied into a plugin. Preserve it in version control; do not erase history to reuse an old version.

Exact prepared artifacts and receipts live in `.local/prepared-releases/PROFILE/VERSION-HASH/`. These directories retain earlier candidates when the working output changes. Compare the saved hashes before using a previous candidate. Preparing rollback means selecting a verified prior artifact and reviewing its current retirement policy; activation still requires separate authorization. Version edits have their original configuration copies under `.local/version-backups/` for local recovery.

All 15 removed predecessor names and Prose Pass are blocked as standalone entrypoints and managed destination aliases. Their recorded embedded modes remain preserved. Canceled Explorer is excluded from active inventories and dependency payloads; its original directory may remain untouched beside active sources. Ordinary activation refuses retired aliases, including aliases from older releases. The existing explicit `restore RECEIPT` recovery operation remains available for an authorized reversal; never use it as an ordinary release route or to silently reinstate a retired skill.

Interactive Proposal's personal account copy is disabled. Its permanent deletion remains unapproved. A local release receipt does not change that account state or establish account synchronization.

## Format references

The [publishing guide](https://code.claude.com/docs/en/plugins/publish) explains that an explicit plugin version must change for users to receive updated bytes. These formats were checked on 30 October 2026; inspect current host validation before distribution.
