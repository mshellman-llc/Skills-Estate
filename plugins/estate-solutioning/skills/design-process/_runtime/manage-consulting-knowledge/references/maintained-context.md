# Maintain uploadable subject context

Use the project's registered subject Markdown when new work changes the client,
the owner's work, a workstream, findings, decisions or outcomes. Project guidance
or the Hub response selects the files and write adapter. Keep private client
paths and subject lists in that configuration, outside the reusable skill.

## Trigger from the work

Run this procedure when ordinary work adds or changes durable knowledge. Meeting
findings, a changed requirement, a tested implementation result and a corrected
work report qualify even when the request names only the immediate deliverable.
Keep the requested delivery skill as the main workflow; knowledge upkeep is its
completion step. It does not require a separate user request.

| Normal request | Knowledge work |
| --- | --- |
| Explain what changed in this client standup. | Capture supported changes and reconcile the affected workstream, owner-work and findings MDs. |
| Refine these requirements using the new interview. | Keep the requirements workflow, then reconcile changed business rules and findings into their existing owners. |
| The integration test passed; update the delivery report. | Retain the test's scope and result, update the delivery and outcome context, and preserve earlier failed attempts as history. |
| Find the last agreed scope. | Retrieve the current authority. With no new finding, keep the MDs and dates unchanged. |
| Fix the formatting in this brief. | Keep its facts intact. Record that presentation changed without adding subject knowledge. |

Read-only retrieval does not authorize a new business fact. A proposal stays a
proposal, a test result retains its environment and a historical source keeps its
effective date. Never manufacture a change to demonstrate the trigger.

## Resolve the maintained files

Check whether the configured Hub names maintained subject MDs. Existing authority
files without required upkeep are a configuration gap, even when the queue is
empty. Read those files and register them in place through the supported adapter;
do not create another summary merely to fit an export folder. Keep formal record
writes on their required writer path.

When a subject has durable sources but no useful MD, reconcile the source into a
substantive client or workstream file and register it before reporting the work
finished. Keep historical research separate from evidence of the owner's role.
An empty folder or a media collection does not need an invented project story.

## Capture and reconcile

1. Preserve the dated source and classify its supported claims. Read the existing
   subject context before changing it. Keep proposals, estimates and completed
   outcomes distinct. A meeting summary locates evidence; it cannot verify itself.
2. Capture the source or substantive Hub update before editing the maintained
   files. When the adapter returns a pending refresh, keep its event key and
   affected subjects. Select the relevant subjects when the service supports
   that field. An omitted selection can require review of the full registered set.
3. Reconcile the new evidence into each affected subject file. Replace a
   superseded current answer; retain dated history only where it explains a
   decision or conflict. Correct other living summaries that carry the changed
   claim. Preserve historical submissions and supplied sources.
4. Keep the existing filenames and subject boundaries. Add a workstream file
   only when it has substantive content, then register it and update the upload
   index. Inventories, build logs and raw transcripts remain supporting evidence.
5. Advance a subject's evidence date only when the source supports that subject.
   Review unchanged subjects with a source-specific reason. A new capture date
   cannot refresh old evidence.

## Write and confirm

Use the configured write adapter and its observed revision or expected hash.
Formal records retain their record-review gates. Editable upload exports use
their declared file adapter; they must not become a bypass copy of a blocked
formal record. Apply the owner's writing rules at the depth required for the
reader. Owner-only context stays private.

Read back each saved file and compare its meaning with the source. When the Hub
provides complete_knowledge_refresh, submit every affected subject's disposition,
current hash and reason using the discovered schema. An updated disposition
requires a content change; metadata alone is insufficient. An unchanged
disposition requires the original hash and the reason the source changes no
claim. Confirm retrieval through the actual index after a content update.

Keep pending refreshes visible until confirmation succeeds. Resume them at the
next context load. A session note or output registration cannot close them. If
access prevents the update, retain the source and pending state with the exact
next action; report the Markdown as pending. On a surface without a refresh
service, record the same file-level comparison and read-back in the existing
session record rather than creating another database.

## Finish line

The source is preserved, affected subject Markdown contains the supported
current answer, superseded claims are reconciled, filenames remain stable,
read-back matches the intended text, and retrieval returns the saved version.
State the actual layer reached. Files on disk, an index refresh and installation
of this workflow in another host are separate results.
