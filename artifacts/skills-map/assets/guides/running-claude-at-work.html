AI 201 operations edition

Set up Claude across a business and every client repository it touches.

The builder edition ran one kitchen. A consulting practice runs a restaurant group: head office sets rules for every location, each restaurant keeps its own binder, and every cook brings their own knives. This edition covers where Claude’s instructions and settings live, which one wins, and how to carry context from one session to the next without burying Claude in it.

Four layers1 of 9

Claude Code reads instructions and settings from four layers.

Instructions from every layer add together. Settings can conflict, and the narrower layer wins, except that organization policy always wins.

1 of 4

Head office sets the rules every location follows.

Your IT or Claude admin sets these once for every person. Nobody can override them from their own machine.

Instructions
A managed CLAUDE.md at /Library/Application Support/ClaudeCode/CLAUDE.md on a Mac, /etc/claude-code/CLAUDE.md on Linux.
Settings

When two settings disagree, this order decides.

Organization policy comes first and can’t be overridden. A flag you type when starting a session comes next. After that, the narrower file wins: local over project, project over personal.

Lists such as allow and deny rules combine across files instead of replacing each other.

Surfaces2 of 9

Each Claude surface has a place for standing instructions.

Claude apps call it project instructions. Claude Code calls it CLAUDE.md. Your own app sends it as the system prompt.

SurfaceStanding instructionsReference materialFits
Claude appsProject instructionsFiles added to the projectDrafting, analysis and research where a person reviews every answer.
Claude CodeCLAUDE.mdFiles in the repository, read when neededWork that lives in files: code, proposals, configuration, documentation.
Claude API and Agent SDKThe system promptWhatever your code sendsA repeatable job your own product runs for customers.

Pick the surface by where the work lives.

A proposal drafted with a client team fits a project in the Claude apps. A configuration change kept in git fits Claude Code, even when the files are documents rather than code. A job that runs a thousand times a month for customers fits the API.

CLAUDE.md and AGENTS.md3 of 9

CLAUDE.md is Claude’s file, and AGENTS.md is the one every agent shares.

AGENTS.md is an open format that Codex, Cursor and other coding agents read. Claude Code reads AGENTS.md only when no CLAUDE.md exists, so a repository with both bridges them with one import.

An @ followed by a path inside CLAUDE.md pulls that file in at the start of the session. Imports can nest up to four levels deep.

Keep each CLAUDE.md under about 200 lines. A longer file uses more of the context window and Claude follows it less closely.

CLAUDE.md in a repository that also serves Codex and Cursor
@AGENTS.md

## Claude only
Use plan mode before changing anything under billing/.

The first line imports AGENTS.md, so every agent reads the same instructions. Anything below it applies to Claude alone.

What loads at the start, and what waits.

Loaded at the start

  • The organization's managed CLAUDE.md.
  • Your personal ~/.claude/CLAUDE.md.
  • Every CLAUDE.md and CLAUDE.local.md from the folder you started in up to the root.
  • Rules in .claude/rules/ that have no path filter.
  • The first 200 lines of auto memory.
  • The name and description of each skill and subagent.

Loaded when needed

  • A CLAUDE.md in a subfolder, when Claude reads a file in that subfolder.
  • A rule with a path filter, when Claude works on a matching file.
  • The full text of a skill, when a request matches its description.
  • The rest of auto memory, when Claude opens a topic file.
  • Any file Claude reads to do the task.

1 of 2

  • Write the build, test and lint commands exactly.
  • Name the folders and what lives in each.
  • State the conventions a newcomer would get wrong.
  • Point to a longer document with an @ import or a path, and keep the detail there.
  • Say why a rule exists, so Claude can apply it to cases you didn’t list.

2 of 2

  • Paste a style guide a linter already enforces.
  • Keep instructions for a tool the team stopped using.
  • Put a secret, a password or a customer’s data in it.
  • Repeat what the code already makes obvious.
  • Let it grow past what a new teammate would read on day one.

Change the project layer the way you change code.

  • Treat a change to CLAUDE.md, settings or skills as a code change, with a pull request and a reviewer.
  • Name one owner for the project layer in each client repository.
  • Write the reason in the pull request, so the next person knows whether a rule still applies.
  • Start a new client repository from a template that already has the project layer.
Carrying context6 of 9

Everything loaded at the start of a session is paid for in every session.

The context window is everything Claude can see at once. When it nears full, Claude Code summarizes older turns on its own.

Point, don’t paste

Link the API guide from CLAUDE.md. Claude reads it when a task needs it, and it costs nothing in other sessions.

Split by path

Put billing rules in a rule file limited to billing/. They load only when Claude touches billing.

Move procedures to skills

A ten-step release checklist belongs in a skill. Only its description loads until someone asks for a release.

Send research to a subagent

A subagent reads forty files in its own context window and hands back a summary.

Write the handoff down

End a long task with a short note in the repository: what changed, what is left, what was decided.

Clear between tasks

Use /clear when you switch to unrelated work. Use /compact to shrink a long conversation and keep going.

Auto memory keeps what Claude learns between sessions.

Claude Code writes notes about a project, such as a build command or a correction you gave, to a memory folder on your machine. It loads the first 200 lines of the index each session and reads the rest when needed. Run /memory to read, edit or turn it off.

CommandWhat it does
/initReads the repository and writes a first CLAUDE.md.
/memoryOpens your CLAUDE.md files and auto memory to edit, and turns auto memory on or off.
/contextShows what is using the context window right now. /context all also lists the instruction files that loaded.
/compactReplaces the conversation so far with a summary. Add a focus, such as /compact keep the test failures.
/clearStarts a fresh conversation in the same session.
Rolling out7 of 9

Take a client from one pilot team to the whole organization.

Every correction in the pilot becomes part of the layers.

Step

Pick one team and one workflow

Choose work that repeats weekly and has a clear right answer, such as preparing a release or reviewing a configuration change.

1 of 6
1Pick one team and one workflow
2Set the organization layer
3Build the project layer in a pilot repository
4Log every correction
5Package and roll out
6Review each month
  1. Pick one team and one workflow. Choose work that repeats weekly and has a clear right answer, such as preparing a release or reviewing a configuration change.
  2. Set the organization layer. Turn on single sign-on, then set managed settings: deny rules for secrets, approved MCP servers and marketplaces, and no skipping permission prompts.
  3. Build the project layer in a pilot repository. Run /init, cut the result to what a new teammate needs, and commit CLAUDE.md, settings.json, .mcp.json and the first two skills.
  4. Log every correction. Each time someone corrects Claude, decide where the fix goes: a CLAUDE.md line, a rule, a skill or a hook.
  5. Package and roll out. Bundle the skills, subagents, hooks and MCP servers into a plugin, and publish it from a team marketplace.
  6. Review each month. Remove instructions that no longer apply, check usage and cost by team, and move repeated corrections into the plugin.

Guardrails8 of 9

Set the limits in settings, because Claude can’t skip a setting.

Deny rules

Block reads of .env files and secrets folders in the organization layer, where no one can remove them.

Permission modes

Default asks before each edit and command. Plan mode reads and proposes without changing anything. Administrators can turn off auto mode and the mode that skips prompts.

Hooks

A hook runs a script before or after a tool. It can block a command, run tests or format a file, and it runs every time.

Least access for MCP

Give each server the narrowest account it needs. A read-only CRM user for research, a sandbox for writes.

Approved sources

Limit plugins to your team’s marketplace and MCP servers to an approved list.

Unattended runs

claude -p runs one task with no chat. Without --bare it runs the repository’s hooks and connects its MCP servers with no approval prompt, so add --bare in CI.
